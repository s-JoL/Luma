# Luma — 产品定义

这一份只写：这是什么、为谁、不做什么、为什么。没有 schema，没有路由，没有
字段表。那些在 `01`–`09` 里，而这一份是读它们之前该读的东西。

它存在的原因是：在它之前，九份文档近 5800 行，按架构、数据模型、API、工具
组织，每一份都能回答「这里怎么实现」，没有一份回答「这是给谁的、什么算做完
了」。原则散在各文档的 Constraints 与 Rejected alternatives 里，盘点出 38
条，读起来像缺陷记录而不是一套立场。

---

## 定位

**一个人的创作工作站。** 写作、图文、画图、视频，跑在自己的机器上，用自己的
模型和自己的密钥。

三件事是它的形状，其余都是从这三件推出来的：

1. **任何后端都能插进来。** 托管 API、中转网关、本地 llama.cpp、本地
   ComfyUI，都是一行模型配置加一个 adapter，不是一次发版。
2. **一切留在本机。** SQLite 和文件目录就是全部的状态。没有账号，没有云端，
   备份就是拷一个目录。
3. **任何客户端远程可达。** 服务端是唯一的真相，浏览器只是一个客户端；手机
   上打开同一个地址，看到同一个会话。

## 主用途，按重要性排序

排序是有用的，因为它决定取舍：两个需求冲突时，靠前的赢。

1. **长篇写作。** 一次几千字，连着几十轮，上下文要活得下来。
2. **图文连载。** 文字与配图交替，同一批人物与画风要能延续。
3. **画图。** 单张、成组、改图，参数要能被看见也能被复现。
4. **短视频。** 从文字或从一张图起。

**联网搜索、文件检索、记忆、代码执行都不在这个排序里**，因为它们不是用途，
是让上面四件事做得成的条件。它们该好用，但它们不是产品的中心；一个只会搜索
的 Luma 是没有意义的。

## 非目标

写下来是为了以后不必再论一次：

- **多人协作。** 没有多用户，没有权限模型，没有共享。访问码之上就是本人。
- **公共托管。** 不为陌生人运行。这直接决定了安全边界的位置（见下）。
- **第三方分发。** 生成的东西不打算发布到别处去，也就不需要发布用的那一套。
- **内容过滤。** 过滤在上游与下游的专门组件里，不在这里重复一遍
  （见仓库根的 `AGENTS.md`）。
- **自研模型。** 不训练、不微调、不做模型选型的评测平台。
- **遥测。** 不上报任何东西。日志留在本机，给本人看。

## 原则，三层

38 条盘点收敛成三层。分层是因为它们的强度不一样：第一层是不许违反的，第二层
是有更好理由才能违反的，第三层是已经付过代价的记录。

### 一、硬约束

违反它们等于变成另一个产品。

- **单人自用。** 任何设计不必考虑第二个人的存在，也不许假设只有一台设备。
- **本地文件是真相。** 数据库与资产目录之外没有别的状态。
- **API-first。** 每个能力都是一个 HTTP 端点，网页是它的第一个客户端而不是
  它的实现。手机客户端要能做的事，浏览器已经在这么做了。
- **密钥只写不读。** 存进去就出不来，界面只显示「已配置」。
- **安全在上层。** 内容安全属于上游与下游，不在生成层重复。访问码与两步验证
  是网络边界的事，不是 prompt 的事。

### 二、优先项

有更强的理由可以让步，但让步要写下来。

- **一处产出，两个受众。** 一个 schema 同时喂创作台的表单和模型的工具，
  两边只允许按声明的受众标记而不同（`08-generation.md`）。两份手写的
  schema 必然漂移。
- **不静默失败。** 宁可报错，不可假装成功。摘要器曾静默失败，代价是一整段
  对话悄悄少了上下文。
- **状态可推理。** 一行记录就是一件事的全部状态，客户端读它就够，不必重放
  事件流（`08-generation.md §Jobs`）。
- **拒绝要给理由。** 每次说不，要说清是什么不行、以及该改什么。给模型的和
  给人的都算。
- **准一次落库。** 花过钱的渲染不许丢，也不许因为重试而付两次。
- **agent 的活动始终可见。** 工具调用、思考、排队都摊在对话里。曾提过一个
  隐藏这些的「阅读态」，被明确否掉：知道 agent 在做什么本身就是需求，不是
  噪音。

### 三、已付过代价的教训

按 ADR 的方式记：出过什么事，现在怎么做。删掉一条之前，先确认那件事不会再
发生。

| 出过的事 | 现在的做法 |
|---|---|
| `events` 表长到 310 MB | 事件按 run 修剪，转写进 `messages` 后不再留存 |
| 一次失败的登录锁死整个部署 | 锁按来源计，不按部署计 |
| 摘要器静默失败，对话悄悄丢上下文 | 摘要失败是错误，向上报 |
| 每轮重发全部历史图片，prompt cache 全丢 | 历史里只留图片的 id，要看再调 `view_image` |
| job watcher 随 effect 重建，连接泄漏 | watcher 放在 ref 里，只在卸载时关 |
| 字符数截断把编译错误砍成一半 | 按行与字节截，并说明省掉了多少 |
| 提交超时后重试，同一个渲染排了两次队 | 客户端生成 prompt id，重试前先问后端认不认 |

## 两个决定，和它们的理由

这两条是这一版明确「不做」的，理由写在这里，以后要翻案得先驳掉理由。

### 长篇作品实体：暂缓

**想做的是**：一个「作品」，有章节、有插图位、能重排、能局部重生成、能导航。

**为什么现在不做**：现在的编辑是回退。改一条用户消息意味着删掉它之后的全部
消息（`fromSeq`），这在对话模型里是对的——但它无法支撑「回去改第十章、
保留后面二十章」。作品实体要的是文档语义，transcript 给的是时间语义，两者
不是同一个东西。

真要做，得逐字节对齐 `messages` 与 `image_assets` 两套血缘，再加一层人工
维护的结构；做错了会丢数据，而丢的是几万字。

**代价**：长篇写作是第一主用途，它现在只能靠对话本身承载。这是清楚记在账上
的欠债，不是没想到。

**存疑**：`07-ios-app-prd.md` 写着「transcript 是 agent 唯一的记忆」。它
和作品实体是矛盾的——那句话是当下实现的前提，不是永远的立场。真要做作品实
体，先驳掉它。

### 导出：不做

**为什么**：东西是在应用里读的。没有分发需求，也就没有导出需求。写好的一章
下一步是被继续写，不是被变成 PDF 交给谁。

一个应用如果是自己读东西的终点，那么真正的障碍是噪音而不是格式转换——所以
力气花在应用里读得舒服上，而不是花在生成一个没人会打开的文件上。

**会重新考虑的条件**：出现了真实的分发场景。目前没有。
